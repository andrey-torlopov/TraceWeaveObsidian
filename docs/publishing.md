# Сборка, проверка и публикация TraceWeave для Obsidian

Репозиторий: [andrey-torlopov/TraceWeaveObsidian](https://github.com/andrey-torlopov/TraceWeaveObsidian). Версия этой инструкции — 0.2.0. Установка пользователем описана [здесь](ru/installation.md); документация веб-версии и её Docker-дистрибутив находятся в [отдельном репозитории](https://github.com/andrey-torlopov/TraceWeave).

## Что публикуется

Исходники плагина, README на двух языках, документация и иллюстрации, manifest/versions, условия [LICENSE](../LICENSE) и [уведомления зависимостей](../THIRD_PARTY_NOTICES.md). Тестовые vault, исследовательские файлы, `.env`, ключи, `node_modules` и локальные runtime-каталоги не публикуются. ZIP собирается из явного списка программы и документации, а не из рабочей папки целиком.

`main` — основная ветка. Её переименование из `codex/obsidian-hidden-data` не меняет содержимое или связи исследований: ветка относится только к исходникам программы.

Собственный код плагина публикуется под MIT по решению владельца. Условия находятся в LICENSE; лицензии включённых компонентов сохраняются в отдельных уведомлениях.

## Локальная проверка

Нужна версия Node.js из `package.json`. Из корня репозитория:

```sh
npm ci
npm run verify:public
npm run generate:validators
npm run lint
npm test
npm run package
npm run verify:public -- --package
git diff --check
```

`verify:public` проверяет согласованность версий, лицензию, локальные ссылки документации, опасные имена файлов и характерные абсолютные пути машины. Он не заменяет secret scanner. Дополнительно используйте **Gitleaks 8.30.1**, без вывода значений находок:

```sh
gitleaks git . --log-opts='--all --full-history' --redact --no-banner --ignore-gitleaks-allow
gitleaks dir release/0.2.0 --redact --no-banner --ignore-gitleaks-allow
```

CI выполняет проверки при push/PR и не публикует релизы автоматически. Для нового version tag отдельный job создаёт GitHub build provenance attestations для трёх compiled assets; upload-artifact сохраняет именно эти проверенные байты. Линтер использует официальный recommended-конфиг Obsidian без отключения правил. В CI закреплены версии инструментов; бинарный Gitleaks проверяется по опубликованной контрольной сумме. Не добавляйте suppressions для настоящих секретов. При находке уже опубликованного ключа сначала отзовите/замените его; очистка нового commit не удаляет историю или скачанные копии.

Проверьте ZIP по CRC и `SHA256SUMS`, установите его в отдельный синтетический vault и проверьте открытие исследования, заметки, связи, материалов, restart, backup и import. Для 0.2.0 дополнительно проверьте выбор существующей заметки без копирования, создание новой по штатной настройке Obsidian, двойное нажатие → открытие, диагностику удалённой заметки и повреждённого original, красную подсветку и восстановление привязки. Проверьте видимые `TWData/projects` и `TWData/exports`, стабильность имени папки после изменения названия исследования и перенос корня с восстановлением прерванного журнала. Проверенный профиль прежних выпусков: desktop Obsidian **1.14.4**, macOS; новые проверки фиксируйте отдельно по фактическому результату. Windows/Linux и все кодеки не объявляются полностью проверенными. Не используйте реальные материалы для тестов.

## GitHub Release

Согласуйте `package.json`, lock-файл, `manifest.json` и `versions.json`. Для 0.2.0 минимальная версия приложения — 1.14.4; версия установщика не доказывает совместимость со старым runtime.

После проверок и push `main` создайте релиз с тегом **`0.2.0`** — точно как `manifest.version`, без префикса `v`. К релизу приложите **отдельные** файлы из `release/0.2.0/`:

- `main.js`;
- `manifest.json`;
- `styles.css`.

Другие файлы к GitHub Release не прикладывайте: Community directory отмечает их как неподдерживаемые. ZIP и SHA256SUMS остаются локальными результатами `npm run package`. Полные лицензии программы, Unicode и реально включённых библиотек добавляются в конец `main.js`. Source code ZIP, который создаёт GitHub, не заменяет compiled assets. Сначала скачайте artifact `attested-plugin` успешного tag workflow и проверьте совпадение с локальной сборкой. Публикуйте эти три файла. После публикации скачайте assets заново без авторизации, сравните hashes и выполните `gh attestation verify <file> --repo andrey-torlopov/TraceWeaveObsidian` для каждого файла. Уже опубликованные байты под прежним тегом не заменяются: исправление получает новый номер.

README/manifest должны находиться в корне основной ветки. Поле `id: traceweave` — имя папки установки; менять его после распространения без миграционной стратегии нельзя.

В release notes 0.2.0 укажите изменение layout и необходимость полной копии vault до обновления. Возврат к 0.1.6 требует восстановления скрытых метаданных до миграции; сохранение старых originals не делает замену одного bundle достаточным откатом. Укажите, что папка новых заметок задаётся в Obsidian, а **Папка данных** управляет только материалами и экспортом. Готовые отчёты и исторические снимки при смене корня не перемещаются.

## Подача в Community plugins

**GitHub Release не добавляет плагин во встроенный поиск автоматически.** Актуальная [официальная инструкция](https://docs.obsidian.md/Plugins/Releasing/Submit%20your%20plugin) использует [Community directory](https://community.obsidian.md), а не старый порядок через pull request в список релизов.

TraceWeave уже имеет [карточку в каталоге](https://community.obsidian.md/plugins/traceweave). Для обычного обновления сохраняйте тот же ID и репозиторий, публикуйте новый GitHub Release с тремя compiled assets и проверяйте статус существующей карточки. Не создавайте второй плагин для обновления версии.

При первой подаче нового плагина владелец выполняет:

1. Входит в портал через свой аккаунт Obsidian.
2. Подключает GitHub-аккаунт и подтверждает владение репозиторием.
3. Открывает **Plugins → New plugin**, указывает `https://github.com/andrey-torlopov/TraceWeaveObsidian` и владельца.
4. Проверяет извлечённые сведения из manifest основной ветки.
5. Лично принимает [Developer policies](https://docs.obsidian.md/community-directory/developer-policies) и обязательство поддерживать плагин, затем отправляет форму.
6. Устраняет замечания автоматической проверки новым commit/релизом с увеличенной версией.

Вход в аккаунт и принятие персональных обязательств выполняет владелец. Пока подача/проверка не завершены, документация должна прямо говорить, что плагин ещё не находится через поиск Obsidian. Подробности формы: [Set up and claim](https://docs.obsidian.md/community-directory/set-up-and-claim).

Проверьте уникальность ID в момент первой подачи. `isDesktopOnly: true` остаётся обязательным, пока используются Node.js/Electron. В README раскрывается чтение явно выбранных внешних файлов при импорте. Исследования сохраняются внутри vault; ZIP-экспорты создаются в видимой `<папка данных>/exports/<постоянная папка исследования>/` и показываются в файловом менеджере. **Экспорт отчёта** создаёт отдельную папку с `summary.md`, `scheme.canvas` и `Attachments/` внутри `exports/`; по умолчанию корень — `TWData`. **Папка данных** принимает безопасный относительный путь и создаёт проверенные копии материалов; текущие заметки используют обычные настройки Obsidian. Никаких обещаний автоматической синхронизации с веб-приложением.

## Установка до и после каталога

До одобрения друзья могут установить **BRAT** из каталога Obsidian и добавить `andrey-torlopov/TraceWeaveObsidian`: [инструкция](ru/installation.md#установка-через-brat). Для BRAT нужен опубликованный релиз с compiled assets. После установки или обновления полностью перезапускайте Obsidian; горячее перевключение не является проверенным способом загрузки.

После одобрения: **Настройки → Сторонние плагины → Обзор → TraceWeave → Установить → Включить**. Затем палитра команд → **TraceWeave: Открыть исследование**. Дальнейшие версии Obsidian получает из GitHub Releases.

## Данные и откат

Перед обновлением сделайте полную копию закрытого vault со скрытой `.twdata`. Obsidian Sync её не переносит. Удаление программы не удаляет данные. **Откат с 0.2.0 к 0.1.6 или более старым версиям требует полной копии vault до обновления, а не одной замены bundle.** При обновлении зарегистрированные originals копируются в видимую структуру с барьером истории, старые файлы сохраняются для ссылок, заметки не перемещаются. Недоступные или изменённые originals остаются по старым привязкам и попадают в диагностику. Новые snapshots/retained ZIP создаются видимыми; исторические snapshots, журналы и исходные архивы остаются неизменными. Прерванная смена папки данных отслеживается в `.twdata/layout-change.json` и требует завершения восстановления. [Хранение](storage.md), [backup/import](ru/backup-import.md).

ZIP проекта не является точной копией всего vault: local history/UI cache и незарегистрированные inline-ресурсы не входят в portable backup. Обычные wikilinks/relative paths при ZIP import пока переназначаются не полностью; это ограничение нужно сохранять в release notes, пока оно не исправлено и не проверено.
